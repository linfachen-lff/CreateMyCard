# AI 卡片项目云侧方案设计

本文档是 AI 卡片云侧方案的唯一权威来源。 当本文档与代码实际实现、其它文档内容、skill内容存在冲突时，请询问用户，以哪个为准，并给出你的建议，用户确认后刷新对应的文件内容，保持文档一致性。

核心原则是：**由微服务完成真实能力裁决、最终 CardSpec、A2UI 模型输入构造、DSL 生成、校验、降级和落库；主 Agent 做轻量 SOP、候选选择和用户回复组织；A2UI 模型只生成 genui DSL；端侧负责下载 artifact、渲染、确认添加和运行时刷新。主 Agent 在任何情况下都不自行生成最终 DSL、CardSpec 或替代 artifact。**

主 Agent 不承诺最终一定能生成某类动态卡片，等微服务返回后再组织用户回复。

## 方案目标与范围

本项目服务于小艺 App 的 AI 卡片生成功能。用户在小艺 App 中用自然语言表达卡片需求，例如“帮我做一个通勤日常卡片，包含今天天气和今日会议”，云侧生成可在端侧预览和添加到桌面的 HarmonyOS A2UI Form 卡片。

目标链路是：

```text
 用户在小艺 App 发起卡片生成请求
 -> 主 Agent 识别场景并选择候选能力
 -> 微服务按用户设备实际能力裁决并生成 artifact
 -> 端侧下载 artifact，渲染 DSL 并持久化 DSL + CardSpec
 -> 卡片运行时按 CardSpec 调端侧数据能力刷新 DataModel
```

一期重点只覆盖一方应用和系统能力，例如天气、日历、系统设置、运动健康等。三方 App 数据、跨端数据和复杂页面型需求不作为默认动态能力支持，必须通过能力注册表明确声明后才能生成动态 CardSpec。本方案也暂未考虑需要授权的情况。

其中 App 中控与主 Agent 能力框架本身已具备，云侧主要需要开发的是 Skill 与微服务。

## 端到端流程

```text
Step 1: App 中控根据 App 版本和 ROM 版本决定是否加载 Skill
        ROM < 7.0: 不加载本 Skill
        ROM >= 7.0: 允许 Skill Search / Skill 加载

Step 2: 主 Agent 判断用户 query 是否匹配卡片创建场景

Step 3: 主 Agent 调微服务获取能力概述
        微服务在该接口内查询 IDS 已安装应用清单
        按当前注册表和包名过滤范围完成用户实际数据能力裁决
        返回实际可用数据能力、不可用数据能力 ID、事件能力和素材概述

Step 4: 主 Agent 根据 query 筛选候选能力
        数据能力只从 dataCapabilities 中选择
        unavailableCapabilities 只记录云侧支持但用户本地不可用的数据能力 ID
        数据能力按需调用微服务加载完整 schema
        事件能力和素材能力可在 Step 3 直接返回候选信息

Step 5: 主 Agent 将 query、候选 dataBindings、候选事件、候选素材、size 等信息传给微服务
        工具层自动携带用户 App 版本、ROM 版本、device、uid 等上下文

Step 6: 微服务生成卡片
        6.1 使用能力概述阶段已裁决的候选，校验注册状态、参数和写入路径
        6.2 加载小模型侧记录并由服务配置指定的 A2UI 协议 profile
        6.3 生成最终 CardSpec，构造 TaskSpec / A2UI prompt
        6.4 调 A2UI 模型生成 genui
        6.5 按配置执行 artifact 校验，并由独立开关决定是否重试
        6.6 生成 artifact 文件，上传 OBS，返回链接和结构化状态

Step 7: 主 Agent 收到微服务结果，向用户回复
        success 且需求未因能力不可用而缺失: 返回正常成功说明和卡片生成结果标记
        部分数据不支持但仍有有效 artifact: 返回统一的部分数据不支持说明和卡片生成结果标记
        整体不支持: 返回统一的整体不支持说明，不返回卡片生成结果标记
        其它异常: 返回统一的创建异常说明，不返回卡片生成结果标记
        generateWidgetCard 不可用、调用失败或产物不符合预期: 按其它异常回复并终止本轮

Step 8: 端侧解析文件链接，下载 artifact，渲染 DSL 并持久化 DSL + CardSpec

Step 9: 卡片安装后由端侧负责运行时数据刷新
        9.1 根据 CardSpec 的 dataBindings 和刷新计划确定待执行的数据能力
        9.2 调用端侧数据能力，取得结构符合对应能力 outputSchema 的返回值
        9.3 以 writeResultTo 作为 path、能力返回值作为 value，自动构造新的 A2UI updateDataModel 消息
        9.4 将 updateDataModel 消息注入已渲染 surface 的 A2UI 运行时
        9.5 DataModel 更新后，由已绑定该路径的组件自动重渲染
```

## 系统边界

### App 中控

职责：

- 根据 ROM/App 版本决定是否加载本 Skill。
- ROM < 7.0 时，不召回本 Skill。
- 将必要设备上下文放入会话或工具调用上下文。

不负责：

- 不做能力过滤。
- 不做 DSL 生成。
- 不生成 CardSpec。

### 主 Agent / Skill

职责：

- 识别卡片创建场景。
- 调 `getWidgetCapabilityOverview` 获取能力概述。
- 将 `getWidgetCapabilityOverview` 的 `dataCapabilities` 作为当前用户实际可用数据能力，不自行推测设备能力。
- 只从 `dataCapabilities` 选择数据候选；`unavailableCapabilities` 只用于识别用户本地不可用的数据能力。
- 根据用户 query 选择候选数据能力、候选事件能力和候选素材。
- 按需调 `getDataCapabilitySchemas` 获取数据能力完整 schema。
- 生成候选 `candidateDataBindings` 或候选能力计划。
- 调 `generateWidgetCard`。
- 根据微服务返回的 `status/artifactUrl` 和已知能力缺失信息组织自然语言回复；仅完整 `success` 使用 `message`，其它状态使用统一话术。
- 当 `generateWidgetCard` 不可用、调用失败或返回产物不符合预期时，按其它异常回复并终止本轮。

不负责：

- 正常链路不直接生成 `genui`。
- 正常链路不生成最终 CardSpec。
- 不判断用户设备上能力最终可用。
- 不维护完整 A2UI 协议、组件白名单、样式白名单或美观规则。
- 不向用户提前承诺“可以生成某个动态卡片”。
- 不在工具不可用、调用失败、结果异常或其它任何情况下自行生成最终 DSL、CardSpec、artifact 或替代产物。
- 没有微服务返回的真实有效 `artifactUrl` 时，不输出 `genWidgetResult` 标记。

推荐用户过程话术：

```text
我先检查当前设备支持情况，然后为你生成可用的卡片。
```

### 微服务

职责：

- 维护能力注册表和版本兼容要求。
- 将能力概述接口作为用户实际数据能力裁决入口，在该接口内查询 IDS 已安装应用清单，并按配置范围过滤数据能力。
- 生成阶段消费已经裁决的候选，补充完成参数和写入路径校验。
- 生成最终 CardSpec。
- 加载服务配置指定的 A2UI 协议 profile；profile 与版本的对应关系由小模型侧记录维护。
- 构造 TaskSpec、A2UI system prompt 和 user message。
- 调 A2UI 模型生成 DSL。
- 校验 DSL/CardSpec/artifact。
- 处理降级、拒答、失败重试。
- 上传 OBS，返回 artifact 链接、结构化状态和用户可读信息。

第一期不要引入复杂工作流引擎，普通服务编排即可。

### A2UI 模型服务

职责：

- 根据微服务构造的输入生成 `genui` DSL。
- 微服务对外只暴露异步 `A2UIModelClient.generate()`；其内部统一委托 `UnifiedModelClient.generate()` 完成
  物理模型选择、模型异常重试和主备切换。工具请求不能指定或覆盖模型后端。
- 路由后端分为 `mep` 和 `openai`。第三接口默认使用 `mep`，第四、第五接口默认使用 `openai`，两项
  服务端配置均只允许选择这两个后端；配置错误时启动失败，不执行旧值自动迁移。
- `mep` 保留已有 `/predict` 异步流式实现。`openai` 默认使用 DeepSeek Platform 作为 master、现有
  `cloud/custom/llmclient.py` 作为 fallback；master/fallback 只能通过服务配置选择
  `deepseek_platform` 或 `llmclient`，不能配置为相同客户端。
- `enable_openai_fallback` 独立控制 `openai` 路由是否允许主备切换，默认开启；关闭后 master 模型异常
  重试耗尽即返回失败，不调用 fallback。模型失败重试总开关关闭时仍只调用 master 一次。
- DeepSeek Platform 使用异步 WebSocket；现有同步 llmclient 继续由专用线程池适配。三种物理客户端
  共享 DSL 提取、异常映射、进程级并发控制和超时策略；第四、第五接口无论选择哪个路由后端，都额外
  执行各自的确定性 A2UI 转换。
- MEP 返回 `6241/Early stop due to aborted` 时，如果第四接口已经收到非空 Design DSL 候选，不在传输层
  直接丢弃，而是交给严格 Design 转换器和校验链路判断；没有候选内容或其它接口仍按模型失败处理。

不负责：

- 不查询用户设备能力。
- 不生成或修改最终 CardSpec。
- 不判断用户是否安装 App。
- 不自行选择未过滤能力。

### 端侧

职责：

- 解析 `genWidgetResult` 标记。
- 下载 artifact。
- 渲染 DSL。
- 用户确认后持久化 DSL + CardSpec。
- 根据 CardSpec 的 `dataBindings` 和刷新计划调度运行时刷新。
- 解析每个 binding 的 `capabilityId`、`arguments` 和 `writeResultTo`，调用对应端侧数据能力。
- 保证或校验能力返回值结构符合该能力注册信息中的 `outputSchema`。
- 将能力返回值自动编译为新的 A2UI `updateDataModel` 消息并注入对应 surface；其中 `path` 取自 `writeResultTo`，`value` 为能力返回值。
- 由 A2UI `DataModel` 与组件绑定机制完成局部状态更新和界面重渲染，不要求云侧参与每次刷新。

不负责：

- 不在端侧重新生成或修改云侧下发的组件 DSL 和 CardSpec 契约。
- 不要求把运行时能力返回值上传给卡片生成云服务后再刷新。

## Skill 改造目标

当前 Skill 中很多细节需要下沉：

- 下沉到微服务：A2UI 协议、组件限制、美观规则、素材合法性、DSL 校验、重试修复、最终 CardSpec。
- 保留在 Skill：SOP 流程、能力概述筛选、候选 dataBindings 生成、工具调用、用户回复组织。
- Skill 不直接输出 `genui/cardspec` 或生成替代产物；仅在微服务返回真实有效的 `artifactUrl` 时输出 `genWidgetResult` 链接和自然语言说明，否则按对应失败状态回复。

## 主 Agent 调微服务接口

微服务以工具形式提供五个正式能力，并额外提供一个临时指令验证能力。主 Agent 正式调用工具时使用 `invoke(functionName:"工具名", arguments:{bundleName:"com.omega_w_0823.hmservice", ...业务参数},"skillName":"harmony-card-generation-online")`，`arguments` 包含工具 bundleName 和业务参数，不要再包 `params` 外层对象；`skillName` 必须传当前 Skill frontmatter 的 `name`，本 Skill 固定为 `harmony-card-generation-online`，不得省略或传空字符串。线上工具层会默认把用户实际设备环境信息拼接到工具入参中，示例如下：

```json
{
  "content": {
    "odid": "5e64f3e9-0a80-d719-d689-3c36eca5eeb6"
  },
  "userAuth": {
    "user": {
      "userId": "..."
    }
  },
  "deviceInfo": {
    "deviceId": "5e64f3e9-0a80-d719-d689-3c36eca5eeb6",
    "deviceType": "ALN-AL00",
    "sysVer": "EmotionUI_9.0.0",
    "deviceFormation": "phone",
    "udid": "5e64f3e9-0a80-d719-d689-3c36eca5eeb6",
    "romVersion": "CLS-AL30 6.0.0.328",
    "marketingName": "HUAWEI Mate 60 Pro"
  }
}
```

其中 `userAuth`、`deviceInfo` 和 `content.odid` 由工具层自动拼接，无需主 Agent 生成。`content.odid` 可选，服务将其映射到内部设备上下文；缺失或为空时，IDS 查询继续使用服务固定兜底值。服务不再从 `deviceInfo` 读取 `odid`。ROM 字段名固定为 `romVersion`，不读取任何同义或候选字段名；服务从完整值 `CLS-AL30 6.0.0.328` 中抽取主次版本 `6.0`，用于能力清单区间匹配。

主 Agent 每次调用 `invoke` 前必须以当前运行时 `tools` 中对应工具的 schema 为入参唯一依据：

- `functionName` 必须等于工具 schema 的工具名，`bundleName` 必须等于对应工具声明的 bundleName。
- `skillName` 必须与当前 Skill frontmatter 的 `name` 完全一致，即 `harmony-card-generation-online`。
- 除 `bundleName` 外，`arguments` 顶层只能包含该工具 schema 的 `arguments.properties` 已声明字段。
- 必须满足 schema 的 `required`、字段类型、数组元素类型和已声明的嵌套结构；无法可靠补齐必填字段时不得调用。
- schema 未声明的字段一律不传，不得根据 Skill 文案、参考资料、历史示例、内部类名或经验自行补充。
- Skill 文案、参考资料或示例与当前运行时工具 schema 不一致时，以当前运行时工具 schema 为准，并删除不一致入参。
- 数据能力候选中的能力业务参数还必须符合 `getDataCapabilitySchemas` 本轮返回的对应 `inputSchema`，不得编造字段。

主 Agent 调用顺序示例：

```text
invoke(functionName:"getWidgetCapabilityOverview", arguments:{bundleName:"com.omega_w_0823.hmservice", ...},"skillName":"harmony-card-generation-online")
invoke(functionName:"getDataCapabilitySchemas", arguments:{bundleName:"com.omega_w_0823.hmservice", ...},"skillName":"harmony-card-generation-online")
invoke(functionName:"generateWidgetCard", arguments:{bundleName:"com.omega_w_0823.hmservice", ...},"skillName":"harmony-card-generation-online")
invoke(functionName:"generateWidgetCardTerseDslNested2", arguments:{bundleName:"com.omega_w_0823.hmservice", ...},"skillName":"harmony-card-generation-online")
```

五个正式工具及临时指令验证工具均使用 WebSocket 插件协议。服务在处理期间发送心跳帧；start、partial 和 final
帧的 `reply.items` 始终为空数组。插件顶层 `errorCode` 始终为 `"0"`，`errorMessage`
始终为空字符串；业务失败和路由异常不能修改这两个插件接入字段。final 帧的
`reply.streamInfo.streamContent` 携带完整 `str(legacy_message)`；存在业务错误码时，
先增加“参数异常、版本不支持、模型生成异常、校验异常、产物保存异常、来源产物异常、超时或
服务异常”等面向主 Agent 的中文说明。说明必须同时包含异常原因、建议的下一步动作和
“报错信息如下”，再保留旧消息中的实际 `errorCode`、错误详情和业务数据。例如参数错误以
“工具参数传入有误，请检查必填字段、字段类型和字段取值后重新调用。报错信息如下：”开头。

`generateWidgetCard`、`generateWidgetCardCompactDsl` 和 `generateWidgetCardTerseDslNested2`
支持可选的端侧指令帧，由服务配置
`enable_widget_directive_commands` 统一控制，默认关闭。关闭时不改变现有 start、partial、final
插件帧及业务流程；开启后，新增帧仍使用相同插件外层包络，`reply.items` 仍为空数组，但
`reply.streamInfo.streamType` 和 `textType` 均固定为 `command`，`streamContent` 为标准 JSON
双引号字符串，内容是完整指令对象。

临时接口 `generateWidgetCardCompactDslWithDirective` 的请求、模型后端、版本选择、Design 转换、校验、
repair、artifact 保存和业务响应全部直接复用 `generateWidgetCardCompactDsl`，不新增 Service 方法或生成
策略。唯一差异位于 WebSocket 路由层：该 operation 无条件启用上述指令帧，不受
`enable_widget_directive_commands` 当前值影响；原第四接口仍受全局开关控制。临时能力集中在路由常量、
别名入口、工具 operation/schema 和对应测试中，后续删除时不修改生成主流程。

指令时序：

1. 在首次调用当前路由选定的模型后端之前发送 `AIWidgetStart`，模型异常重试和校验 repair 不重复发送。
2. artifact 上传 OBS 成功并取得非空 `artifactUrl` 后、正常 final 帧之前发送成功的 `AIWidgetEnd`，
   将该 URL 写入 `intentParam.genWidgetResult`。`success` 和具有有效 artifact 的 `degraded` 均按成功处理。
3. 只有已成功发送 `AIWidgetStart` 后，本次生成才会发送对应的终态 `AIWidgetEnd`。模型调用后的 DSL 转换、
   Validator、repair、artifact 保存等阶段导致无有效 artifact 时，在失败 final 帧之前发送失败的
   `AIWidgetEnd`。请求校验、版本或协议选择、来源 artifact 或能力裁决在首次模型调用前失败时，不发送开始或终态指令。

三个指令共用以下完整外层结构；`session` 从当前 WebSocket 请求中的 `session`、`deviceInfo`、
`userAuth` 和 `bundleName` 组装，`messageId` 每次指令单独生成：

```json
{
  "directives": [
    {
      "header": {
        "name": "Action",
        "namespace": "Common"
      },
      "payload": {}
    }
  ],
  "errorCode": "0",
  "errorMsg": "OK",
  "isContainsDialogFinishDirective": false,
  "isDialogFinished": false,
  "isFinal": false,
  "isFinished": false,
  "isIgnoreDialogState": false,
  "session": {},
  "triggerRedLine": false
}
```

开始指令的 `payload`：

```json
{
  "executeParam": {
    "intentName": "AIWidgetStart"
  }
}
```

成功指令的 `payload`：

```json
{
  "executeParam": {
    "status": true,
    "intentName": "AIWidgetEnd",
    "intentParam": {
      "genWidgetResult": "真实 artifactUrl"
    }
  }
}
```

失败指令的 `payload`：

```json
{
  "executeParam": {
    "status": false,
    "intentName": "AIWidgetEnd"
  }
}
```

### getWidgetCapabilityOverview

用途：完成当前用户实际数据能力的前置裁决，使主 Agent 在生成前即可了解可用和不可用的数据能力。

WebSocket path:

```text
/api/v1/ws/tools/getWidgetCapabilityOverview
```

输入：

```json
{}
```

输出应为结构化 JSON，不要只返回自然语言文本。可以额外提供面向 LLM 的描述字段。

```json
{
  "dataCapabilities": [
    {
      "id": "ViewWeather",
      "description": "查询当前天气、空气质量和未来预报"
    }
  ],
  "unavailableCapabilities": ["GetAppUsageDuration"],
  "eventCapabilities": [
    {
      "id": "event.open.weather",
      "description": "打开天气应用",
      "actionTemplate": {
        "call": "clickToDeeplink",
        "args": {
          "intentName": "Weather_CityCode",
          "bundleName": "",
          "abilityName": "",
          "uri": "{{ 'hww://www.huawei.com/totemweather?enterType=share&cityCode=' + ${/data/weather/location/cityCode} }}"
        }
      },
      "dynamicArguments": [
        {
          "path": "/uri",
          "type": "string",
          "description": "cityCode 取自 ViewWeather 的 /location/cityCode，保留完整 URI 模板。"
        }
      ]
    }
  ],
  "assetCandidates": [
    {
      "id": "asset.drop_1",
      "description": "天气雨伞图标"
    }
  ]
}
```

说明：

- `dataCapabilities` 是当前用户实际可用的数据能力概述，不返回完整 schema。
- `unavailableCapabilities` 是云侧支持但用户本地实际不可用的数据能力 ID 字符串数组；字段缺失或为 `[]` 时表示本次没有已识别的不可用数据能力。本期只返回 ID，不返回不可用原因。
- 主 Agent 不为 `unavailableCapabilities` 中的能力加载 schema 或构造数据候选；该字段本期仅适用于数据能力。
- 字段存在但不是字符串数组时，按能力概述 payload 无法完整解析处理。
- `eventCapabilities` 只返回 `id`、用户可理解的 `description`、可直接复制到第三接口的完整
  `actionTemplate:{call,args}`，以及允许主 Agent 替换的 `dynamicArguments`。注册表内部的
  `type`、`targetApp`、`targetScene`、`parametersSchema` 和 `dependencies` 不向主 Agent 暴露。
- 主 Agent 构造事件候选时必须完整深拷贝 `actionTemplate`，不得删除或改写其中任何固定字段；空字符串
  也是必须保留的合法固定值。`dynamicArguments[].path` 是相对 `actionTemplate.args` 的 JSON Pointer，
  只允许按这些路径替换动态值。模板中的动态占位符无法安全解析且默认值也不合法时不构造该事件候选；
  未出现在 `dynamicArguments` 中的字段全部视为固定字段。
- `assetCandidates` 只返回 `id` 和语义明确的 `description`。素材 `src`、`type`、`sceneTags`、
  `minXiaoyiVersion` 等注册信息保留在微服务内部；主 Agent 只向第三接口提交素材 ID，微服务再从同版本
  注册表还原完整素材并写入 TaskSpec。
- 主 Agent 可见出参不暴露 `apiVersion`、`capabilityRegistryVersion`、`protocolProfileId` 等版本信息；这些信息只进入日志、artifact meta 和排障链路。
- 能力注册表通过 `cloud/data/capabilities/registry_ranges.json` 对规范化 App/ROM 版本做二维左闭右开区间匹配。当前 App 区间为 `[11.7.5.205, 12.0.0.0)`，ROM 区间为 `[6.0, 7.0)`，命中 `app-11.7.5.205_rom-6.0`。未命中或目标目录不可用且默认回退开关开启时，使用默认目录；该开关默认开启。
- IDS 数据源由独立配置开关控制，默认使用 mock。mock 模式只读取配置文件，文件缺失或内容无效时返回空 IDS 结果，不自动访问远程 IDS；关闭 mock 后只访问远程 IDS，也不反向回退 mock。
- IDS 安装过滤包名范围可配置，默认只包含运动健康包；概述接口只对命中该范围的依赖进行包名精确匹配。

用途：首次生成和多轮编辑共用的主接口。

WebSocket path:


推荐入参：

```json
{

  "size": "2x4",
  "title": "通勤助手",
  "description": "天气日程速览",

    {

        "/location/districtName",
        "/current/temperatureText",
        "/current/condition",
        "/daily/0/condition"

    },
    {
      "capabilityId": "GetCalendarEvents",
      "arguments": {
        "futureDays": 1
      },
      "writeResultTo": "/data/calendar",
      "candidateOutputFields": [
        "/events/0/title",
        "/events/0/dtStart",
        "/events/0/eventLocation"
      ]
    }
  ],
  "candidateEventCandidates": [
    {
      "capabilityId": "event.open.weather",
      "action": {
        "call": "clickToDeeplink",
        "args": {
          "intentName": "Weather_CityCode",
```

说明：

- `sourceArtifactUrl` 为可选的上一版完整 artifact 永久 OBS URL。缺失表示首次生成；传入非空值表示基于该 artifact 编辑。首次生成不要传空字符串。
- 只有 `widget-artifact-v2` 产物可作为多轮编辑来源；旧版 artifact 缺少完整候选计划时不得反向猜测或静默迁移。
- edit 模式下，`userQuery` 只表达本轮修改需求；主 Agent 不下载来源 artifact，也不把历史 DSL 拼入请求。
- create 模式下，省略 `size` 时统一使用 `2x2`；显式传入 `2x2` 或 `2x4` 时继续尊重调用方建议。
- edit 模式下，省略 `size` / `title` / `description` 表示从来源 CardSpec 继承；显式传入时表示替换对应建议值并由微服务重新裁决或规范化。
- edit 模式下，省略某类候选数组表示从来源 artifact 继承并重新校验；显式传入数组表示编辑后该类别的完整候选集合，空数组表示清空该类别。
- 微服务不再对 `sourceArtifactUrl` 执行协议、host、端口、query、fragment 或对象前缀白名单校验。mock 模式只使用 URL path 中的文件名读取本地 mock 对象；remote 模式将原始 URL 交给公共下载方法，因此调用方和部署网络必须保证来源 URL 可信。
- 来源 artifact 加载或校验失败时不得静默转为首次生成；编辑失败不得覆盖来源 artifact。
- 每次编辑必须生成新的完整 artifact 和新 URL，来源 artifact 保持不可变。
- edit 模式不重新查询 IDS。动态能力可用性仍由主 Agent 在能力概述流程中获取；能力发生变化时，主 Agent 必须先刷新能力概述和所需 schema，再提交编辑后的完整候选集合。生成流程只执行注册表存在性、参数、写入路径和结构校验。
- 第三至第五接口共用“模型生成 → 源 DSL Processor → 标准 A2UI Validator → 有限 repair → artifact 保存”
  编排。路由策略一次性确定协议/Profile、模型后端、源 DSL 格式、Processor、编辑/动态能力支持范围和最终
  Validator error 是否阻断，主流程不再按 DSL 变体重复分支。
- `generateWidgetCard` 使用 Standard A2UI Processor；`generateWidgetCardCompactDsl` 使用 Design Compact
  Processor，并沿用同一套 create/edit 语义和 `enable_widget_edit` 开关。create 模式先尝试严格的 Provider
  Template 路由；首层判断不能证明模板完整覆盖本轮 Query 数据时，继续执行原 Design Compact create
  流程。Design Compact 编辑提示词从来源 artifact 的 `designcompactdsl` 代码块读取上一轮 Design Token，
  模型仍只输出完整 Design Compact DSL，再由确定性转换器生成标准 A2UI；edit 模式不执行模板判断，且不得
  使用来源标准 A2UI 作为 Design Token 兜底。
- `generateWidgetCardTerseDslNested2` 的 create 模式保持两次模型调用，但从第一层请求起旁路旧整卡链路。
  第一层使用独立 `advanced-component-scope` 入口，只输出严格、版本化的
  `advanced-scope-brief/1`：`themeId` 和 `advancedComponentIds`。它不得输出旧 `UIBrief`、整卡置信度、
  整卡参数、局部 Template 候选、布局选择、Action 或理由；候选最多下发 8 个语义相关业务高级组件，
  不读取 Fixture ID、Golden 场景或业务名称硬编码。
- 旧 `AdvancedComponentPipeline.generate()`、旧 `UIBrief` Planner、整卡候选评分、置信度阈值、整卡参数
  映射和整卡插件编译代码全部保留，供兼容测试与显式回滚使用，但第五接口 create 主链路不调用它们。
  主链路固定调用新的 `generate_mixed()`；`WIDGET_SERVICE_ADVANCED_WHOLE_CARD_CONFIDENCE_THRESHOLD` 和
  `WIDGET_SERVICE_ENABLE_ADVANCED_WHOLE_CARD_TEMPLATE` 不再改变该接口的 create 路由。
- 第二层 `advanced-mixed-body` 根据第一层 Scope 获取允许的布局高级组件、业务高级组件对应的版本化局部
  Template、TaskSpec 事实和标准组件白名单，直接生成一个已批准的布局高级组件根节点。生产业务区使用
  局部 `Template` 与标准组件；旧直接构造只保留给显式代码级回滚和影子测试。需要 Action 的布局必须把
  Action 高级组件放在最后一个 child；正常成功路径不增加第三个业务规划阶段。第二层严格校验失败时可在
  相同 Scope 下最多校正两次，但不重跑第一层或旧整卡 Planner。
- 布局高级组件同时负责业务区几何和 Action 槽位；`PillAction`、`IconAction`、`ActionTile` 的标签、事件
  和精确尺寸由可信服务端注入。独立 Header 是可选能力且当前默认省略，业务标题由业务内容负责，服务端
  不再把截断后的 Query 强制变成卡片标题。业务高级组件只定义字段、variant、角色、列表预算和局部
  Template 能力，不选择整卡根布局。Selector 的比例、时长、状态和隐私计算保持在可信 Python 端。
- 混合输出由服务端受限 Parser 和 Framer 处理；Parser 只接受声明式字面量、10 个注册布局高级组件、三个
  Action 高级组件、标准组件、Registry 中已注册的版本化 Template，以及显式保留的回滚用直接业务构造，
  不执行 Python 表达式。天气、日期、日程、电量、系统内存、应用使用时长、活动、运动、心率、睡眠和
  蓝牙耳机默认均使用 Provider CardTemplate；视觉树、样式和尺寸重排在可信 Terse UI IR 构造中完成，
  不使用通用脚本。编译器先校验
  布局根、业务子项数量、Action 末位槽位和 Action 条件，再校验素材、字面量、节点、深度、空间预算和
  父子约束；局部
  Template 与布局高级组件均在可信端静态降级为标准组件并复用现有 Terse UI IR/A2UI Adapter。最终
  `genui` 是三段 `v0.9` A2UI，不能包含 `Template` 或任何高级组件名。
- Framer 只在 EOF、字符串已闭合且括号类型顺序明确时补全最多 4 个尾部闭合符；交叉括号、未闭合字符串、
  流中断仍拒绝。Parser 与展开后 UI IR 都拒绝无 children 的 Row/Column/Stack，避免空布局通过协议门禁。
- 新 UX Registry 与旧高级组件 Registry 分开版本化，并与 Template Registry、主题和 Prompt 一同进入
  SHA Manifest。新混合路径使用半径 `20vp`、安全内边距 `12vp`、区块/模块间距 `8vp`、胶囊 Action
  高度 `36vp` 等 UX 设计 Token；模型不能把这些服务端 Token 数值写进 DSL。
- 新混合路线在受限二层校正耗尽后，任一模型协议、解析、展开或校验失败都返回失败，不回退旧整卡入口、
  旧通用 Terse 生成、Golden 或 fixture 产物。edit 模式继续沿用既有完整 Token 编辑链路，避免改变来源
  artifact 语义。
- `options.forceHybridTemplate` 保留兼容和反滥用校验，但 create 主链路已经固定走新混合入口。请求显式传
  `true` 时仍必须同时满足服务配置开启、`WIDGET_SERVICE_ENV` 为 `local` 或 `test`，并提交匹配的非空
  `options.testAuthorization`；生产默认关闭，任一条件不满足均拒绝，token 不写入 artifact 或日志。
- `title` / `description` 是主 Agent 根据用户需求给出的静态展示文案建议，调用 `generateWidgetCard` 时必须传非空字符串，用于微服务生成最终可展示给用户的卡片标题和说明。
- 上述 `title` / `description` 必填规则适用于首次生成；edit 模式允许省略并继承来源 CardSpec。
- `title` 建议不超过 8 个字，`description` 建议不超过 12 个字；两者必须是稳定、静态、用户可理解的文案，不写动态值、隐私内容、未经确认的设备状态或能力可用性承诺。
- `title` / `description` 不替代 `userQuery`，不替代数据能力、事件能力或素材能力；微服务可以按最终能力裁决和降级结果规范化后写入最终 CardSpec 和 artifact 展示元信息。
- `title` / `description` 不进入 TaskSpec 顶层，避免扩展 A2UI 模型输入契约。
- 主 Agent 可见接口出参不暴露版本信息；版本仍必须记录在微服务日志和 artifact meta 中。
- `candidateDataBindings[].candidateOutputFields` 是主 Agent 根据能力 `outputSchema` 和用户 query 筛选出的候选展示字段路径，只表达展示倾向，不改变能力注册表中的原始 `outputSchema`。
- `candidateOutputFields` 是可选字符串数组；每一项都是 JSON Pointer，只允许引用对应能力 `outputSchema` 中存在的字段路径。字段类型、描述、示例值等由微服务根据能力注册表还原，不由主 Agent 传入。
- 不再传 `updateModel`；需要表达候选展示字段投影时只使用 `candidateOutputFields`。无法从 `outputSchema` 推导的路径不得传入。
- `candidateEventCandidates` 是事件候选单数组。
- 每个事件候选必须同时包含 `capabilityId` 和完整 `action.call/action.args`，参数可以是动态路径或静态值。
- `action` 必须完整深拷贝事件能力的 `actionTemplate`；只允许按 `dynamicArguments[].path` 替换动态值。
  `intentName`、空字符串等固定目标参数必须完整保留，不能把参数说明传入生成接口。
- 如果事件 action 无法从能力概述或用户明确输入中安全填齐，不传该事件候选。
- 微服务过滤某个事件能力时删除整个候选项，避免能力 ID 与事件参数错配。
- 本版主 Agent 不传 `slots`；生产默认不传 `options`。本地调试需要内联 artifact 时，才传 `options.returnArtifactInline`。
- 微服务默认 `allowDegradation: true`、`returnArtifactInline: false`。

## 生成接口状态码

`status` 只使用以下枚举：

```text
success      完整满足用户需求并生成成功
degraded     部分能力不可用，已降级生成可用卡片
unsupported  能力或协议限制导致不应生成卡片
failed       系统异常、模型失败、OBS 失败等工程失败
```

不要把 `unsupported` 和 `failed` 混用。

推荐错误码：

```text
SOURCE_ARTIFACT_NOT_FOUND
SOURCE_ARTIFACT_DOWNLOAD_FAILED
SOURCE_ARTIFACT_SCHEMA_UNSUPPORTED
```

## 能力过滤设计

当前能力裁决分为能力概述阶段和生成阶段：

```text
能力概述：根据 prdVer 和 romVersion 的二维版本区间选择能力注册表
 -> 版本目录不存在且回退开关开启时使用默认 205/6.0 注册表
 -> 对配置范围内的 dependencies.requiredPackages[].packageName 查询 IDS 并精确匹配已安装包名
生成阶段：能力 ID 是否注册
 -> arguments 是否符合 inputSchema
 -> writeResultTo 是否合法且无冲突
```

约束：

- `getWidgetCapabilityOverview` 是用户实际数据能力裁决入口；主 Agent 应在调用生成接口前基于其返回结果完成候选选择。
- `generateWidgetCard` 不重新查询 IDS，也不重新执行设备安装能力裁决；它消费能力概述阶段已裁决的候选，只继续执行注册表存在性、参数、写入路径和结构校验。
- ROM/App 当前通过版本化注册表目录完成匹配，不读取 `dependencies` 下的最低 ROM/App 版本字段。
- IDS 当前只消费已安装应用包名，不比较应用包版本，也不校验 provider、intent 或权限。
- IDS 包名过滤范围由配置项维护，默认只包含运动健康包；未进入配置范围的依赖包暂不参与可用性过滤。
- `defaultWriteResultTo` 和 `dependencies` 均为可选字段；缺失时不阻断能力注册表加载。
- 可用性只在能力概述阶段执行；数据 Schema 加载和生成阶段不重复查询 IDS。
- `unavailableCapabilities` 中的数据能力不得进入候选，因此不会进入最终 CardSpec 和 TaskSpec。
- 当前不使用 `PACKAGE_VERSION_TOO_LOW`、`PROVIDER_NOT_FOUND`、`INTENT_TARGET_NOT_FOUND` 等尚未启用的过滤原因；后续扩展对应过滤维度时再同步增加错误码。

## CardSpec 生成

主 Agent 传的是候选 `candidateDataBindings`。微服务过滤后得到 `effectiveDataBindings`，再生成最终 CardSpec。

动态 CardSpec：

```json
{
  "title": "通勤助手",
  "description": "天气日程速览",
  "suggestSize": "2x4",
  "dataBindings": [
    {
      "capabilityId": "ViewWeather",
      "arguments": {
        "districtName": "青浦区",
        "forecastDays": 1
      },
      "writeResultTo": "/data/weather"
    }
  ]
}
```

静态 CardSpec：

```json
{
  "title": "天气入口",
  "description": "快速打开天气",
  "suggestSize": "2x4"
}
```

规则：

- `title` / `description` 使用微服务最终规范化后的静态展示文案，用于端侧预览、添加确认和卡片管理等用户可见场景。
- `title` / `description` 不得包含动态数据值、真实隐私内容、未确认能力可用性承诺或内部字段名。
- `suggestSize` 使用微服务最终尺寸决策，不因静态卡片强制改为 `2x2`。
- 点击事件不进入 CardSpec，只进入 A2UI 模型的候选事件输入。
- 不可用能力不进入 CardSpec。
- 不编造 capabilityId。
- `writeResultTo` 必须位于 `/data/...`。
- 多个 `writeResultTo` 不得相同、互为父子或互相覆盖。
- `arguments` 必须符合能力 `inputSchema`。

## 端侧运行时数据刷新

本节明确 CardSpec、A2UI `DataModel` 和运行时 `updateDataModel` 的职责关系。CardSpec 不是 A2UI `DataModel` 的替代物，也不是另一份运行时状态；它是端侧可执行的数据获取与写入契约。A2UI `DataModel` 是 surface 的运行时状态容器，`updateDataModel` 是修改该状态的 A2UI 消息。

云侧生成阶段与端侧运行阶段的边界如下：

```text
云侧生成阶段
 -> 生成 genui DSL
    - createSurface
    - updateComponents
    - 初始 updateDataModel：只建立初始 DataModel 结构、空值和加载态
 -> 生成 CardSpec
    - dataBindings：声明 capabilityId、arguments、writeResultTo
    - 可选刷新计划：声明何时执行哪些 binding
 -> 将 genui + CardSpec 交付端侧

端侧运行阶段
 -> 读取 CardSpec.dataBindings
 -> 根据安装、可见、周期或其它已声明刷新条件触发 binding
 -> 调用 capabilityId 对应的端侧数据能力，并传入 arguments
 -> 按该能力的 outputSchema 保证、校验或归一化返回值结构
 -> 自动构造新的 A2UI updateDataModel 消息
    - surfaceId：目标卡片 surface
    - path：binding.writeResultTo
    - value：符合 outputSchema 的能力返回值
 -> 将消息注入 A2UI 运行时
 -> DataModel 变化触发绑定组件自动重渲染
```

以如下 binding 为例：

```json
{
  "capabilityId": "ViewWeather",
  "arguments": {
    "districtName": "青浦区",
    "forecastDays": 1
  },
  "writeResultTo": "/data/weather"
}
```

端侧调用 `ViewWeather` 后，若获得符合该能力 `outputSchema` 的返回值 `weatherResult`，则自动构造等价于以下形式的运行时消息：

```text
{
  "version": "v0.9",
  "updateDataModel": {
    "surfaceId": "实际卡片 surfaceId",
    "path": "/data/weather",
    "value": <weatherResult JSON 值>
  }
}
```

上例是消息构造示意，实际 `value` 是符合 `outputSchema` 的 JSON 值。`outputSchema` 由能力注册信息定义，CardSpec 无需重复复制完整 schema；云侧在生成和校验阶段使用该 schema 推导合法绑定路径，端侧数据能力框架在运行时据此保证或校验返回结构。

因此，云侧只需向端侧提供用于运行的 `genui + CardSpec`：云侧负责生成和静态一致性校验，不执行卡片安装后的数据能力调用，也不为每次刷新生成运行时数据。端侧负责刷新调度、能力调用、结果校验或归一化、`updateDataModel` 消息构造与注入。通过该边界，动态数据可以在端侧完成获取和消费，不需要经过卡片生成云服务。

## TaskSpec 构造

TaskSpec 是微服务传给 A2UI 模型的输入契约。`eventCandidates` 由微服务从过滤后的 `candidateEventCandidates` 派生。

顶层只允许：

```json
{
  "userQuery": "...",
  "size": "2x4",
  "eventCandidates": [],
  "dataModelSchema": {},
  "assetCandidates": []
}
```

不要在 TaskSpec 顶层加入：

```text
cardSpec
rules
capabilitySchemas
displayCandidates
role
component
layout
fontSize
dataModel
title
description
```

主 Agent 获取数据能力完整 `outputSchema` 后，可以根据用户 query 在 `candidateDataBindings[].candidateOutputFields` 中选择候选展示字段路径，减少无关字段进入后续生成链路。该字段筛选只作为候选投影，不改变能力注册表中的原始 `outputSchema`，最终仍由微服务校验、补齐和裁决。

`dataModelSchema` 由微服务根据最终 CardSpec、能力 `outputSchema`、主 Agent 候选字段投影和降级结果生成，是传给 A2UI 模型的参考数据结构。它应包含模型生成 DSL 所需的必要根结构、候选展示字段、字段类型、字段描述和实例值，不要求包含能力 `outputSchema` 的全部字段。

规则：

- `candidateOutputFields` 只由主 Agent 传字段路径，不传字段 `type`、`description` 或实例值。
- 微服务校验 `candidateOutputFields` 是否能直接解析到对应能力 `outputSchema` 的叶子字段。部分非法路径被忽略并记录日志；未传投影或全部路径非法时，回退到该能力的全部合法叶子字段。
- 数组字段只接受规范下标 `/0` 表示元素 Schema，其它数组下标不进入投影结果。
- `type`、`description`、`sampleValue` 等字段说明由微服务根据能力注册表、受控样例和场景上下文还原或生成。
- `sampleValue` 表示给 A2UI 模型理解展示形态的实例值，优先使用接近 UI 展示的字符串，例如 `"26℃"`、`"多云"`、`"09:30 产品评审"`；它不代表用户真实运行时数据，也不改变 CardSpec 的动态数据契约。
- `sampleValue` 缺失时不阻断能力加载；微服务按类型生成受控默认值：字符串为 `"示例"`，整数和数字为 `0`，布尔值为 `false`，空值为 `null`。
- 对敏感或私密字段，`sampleValue` 必须使用脱敏样例或占位样例，不得使用真实用户数据。
- DSL 绑定路径仍必须绑定到动态数据路径，不能因为 `sampleValue` 存在而改写为静态文案。

```json
{
  "data": {
    "weather": {
      "location": {
        "districtName": {
          "type": "string",
          "description": "城市或区县名称",
          "sampleValue": "上海"
        }
      },
      "current": {
        "temperatureText": {
          "type": "string",
          "description": "当前温度展示文本",
          "sampleValue": "26℃"
        },
        "condition": {
          "type": "string",
          "description": "当前天气现象",
          "sampleValue": "多云"
        }
      }
    }
  }

```

A2UI 模型可以少用 `dataModelSchema` 中的候选字段，也可以新增受控的静态展示字段或文案辅助字段，但不得在动态数据能力输出路径下编造未授权字段，不得改变最终 CardSpec 所声明的数据能力契约。DSL 实际绑定到的动态路径必须能从最终 CardSpec、能力 `outputSchema` 或微服务允许的 `dataModelSchema` 中推导。

## A2UI 协议 profile

标准生成接口固定加载 A2UI Form profile。Design Compact DSL 接口根据 App/ROM 二维左闭右开区间选择
目标 A2UI profile；该 profile 同时用于 Design Token 转换、校验和 artifact 元数据：

```text
App/ROM -> protocol_profiles/registry_ranges.json
 -> protocolProfileId
 -> 微服务加载组件白名单、属性白名单、尺寸、绑定策略、事件策略、素材策略
```

协议区间索引与能力清单使用相同的版本规范化、边界和冲突规则。未命中区间或目标目录不可用时，
`WIDGET_SERVICE_ENABLE_DEFAULT_PROTOCOL_PROFILE_FALLBACK=true` 才回退到
`WIDGET_SERVICE_PROTOCOL_PROFILE_ID`；关闭时第四接口返回版本不支持。调用方传入的
`protocolProfileId` 不能覆盖接口路由和区间选择结果。

第一期默认遵循：

- `2x2`: `160vp x 160vp`
- `2x4`: `320vp x 160vp`
- `createSurface` 不声明 `width/height`；root `styles.width/height` 必须写 `"matchParent"`，校验和内部布局预算按上述 profile 目标尺寸解析。
- root `styles.borderRadius` 按尺寸设置：`2x2` 为 `18`，`2x4` 为 `22`，并写 `clip: true`；内部组件圆角仍按各自布局和视觉预算确定。
- 内部 Row/Column/Text/Image/Button/Progress 等继续使用可静态推导的数值宽高。
- `catalogId`: `ohos.a2ui.extended.catalog`
- `version`: `v0.9`
- 只允许组件：`Text`、`Image`、`Divider`、`Progress`、`Button`、`Checkbox`、`Row`、`Column`、`List`、`Stack`
- 禁止网络图、内联/base64 SVG data URI、未声明资源路径、未声明事件和禁用组件；允许来自有效素材候选或用户明确提供的本地/资源路径 SVG

绑定与表达式策略：

- 新生成 DSL 优先使用完整 `{{ ... }}` 表达式读取和拼接 DataModel；修复或评审已有 DSL 时，也接受协议声明的 `{"path":"/..."}` PathBinding 和宿主明确注册的 FunctionCall。
- 一个字符串只能包含一对完整表达式，不支持嵌套表达式；表达式内字符串使用单引号，内置函数只允许 `size()`。
- DataModel 推荐使用 JSON Pointer 片段，例如 `"{{ ${/data/weather/current/temperatureText} }}"`；同一卡片内优先保持同一种绑定风格。
- 表达式总长度不得超过 2048 字符，括号嵌套不得超过 20 层；求值失败返回空字符串，不得依赖失败态实现业务逻辑。
- `id`、`component`、对象 key、EventHandler `call`、`updateDataModel.path`、CardSpec `writeResultTo`、模板 `children.path` 和整个 `styles` 对象不允许使用表达式；单个允许动态值的组件属性、样式属性或事件参数可以使用表达式。
- `updateDataModel.path`、CardSpec `writeResultTo` 和模板 `children.path` 是结构 JSON Pointer，不得改写成表达式。

事件链策略：

- Form 只支持通用事件 `onClick`；事件值必须是非空 EventHandler 数组，并且每个事件只允许 1 个 handler。
- 每个 handler 必须包含 `call`；`call` 必须是有效事件候选中已经声明的函数标识符，不允许使用表达式。
- `args` 字段及嵌套结构必须符合对应事件能力的参数 schema 和合法目标；参数可使用安全静态值、完整表达式或协议允许的 PathBinding。
- 不支持 EventHandler `condition`、`as` 和 `$context` 事件上下文，不允许把多个动作串成未声明的行为链。
- 事件参数如果来自数据能力输出，必须能从最终 CardSpec 的 `writeResultTo + outputSchema` 或模板当前项中推导。

新增能力、组件或属性必须先进入 profile 和 validator，再进入 prompt。

## A2UI 模型输入与输出

微服务构造模型输入，不允许主 Agent 直接拼 prompt。

首次生成、多轮编辑和校验修复使用文件化系统提示词配置：首次生成默认读取 `docs/system_prompt.txt`，编辑模式默认读取 `docs/edit_system_prompt.txt`，修复模式默认读取 `docs/repair_system_prompt.txt`。编辑提示词通过 `{{CREATE_SYSTEM_PROMPT}}` 组合首次生成的完整协议和设计约束。修复时在首次调用实际使用的 system prompt 后追加修复约束，因此新建、编辑分别继承原模式约束。三个文件路径均可通过服务配置覆盖。

第三接口把上述标准提示词交给 `WIDGET_SERVICE_A2UI_FORM_MODEL_BACKEND` 选择的路由后端。第四接口 create
模式先执行 `template-route-decision/1` 首层模板判断；判断拒绝或首层输出无法通过服务端完整覆盖复核时，
回到原路径，以 `cloud/data/protocol_profiles/design-compact-dsl/PROMPT.md` 原文作为第一条 system 消息。
原路径 create 模式的第二条 user 消息是纯 TaskSpec JSON，不添加 `TaskSpec:` 等前缀，并交给
`WIDGET_SERVICE_DESIGN_COMPACT_MODEL_BACKEND` 选择的路由后端；模型返回的 Design Compact DSL 必须经过服务内确定性转换器，并使用同目录
`protocol.json` 的版本、catalog 和尺寸参数转成标准三段 A2UI DSL。转换后的 DSL 才进入校验、
repair、artifact 保存和接口响应。第四、第五接口的 edit 模式保持对应 `PROMPT.md` 原文作为第一条
system 消息；第二条 user 消息是单个 JSON 对象，携带本轮 `userQuery`、重建的完整 `taskSpec`、
`previousDesignToken` 和完整输出要求。`previousDesignToken` 来自来源 artifact
`designcompactdsl` 代码块中的上一轮原始 Design Token。来源 Token 是不可信待编辑数据，不得覆盖 system
约束。repair 模式携带当前源 DSL 和转换或校验错误；修复输出会使用本次请求选定的同一后端，重新转换
并校验。
第五接口沿用 `WIDGET_SERVICE_DESIGN_COMPACT_MODEL_BACKEND`。create 模式第一轮使用独立结构化 JSON
Prompt 生成 `advanced-scope-brief/1`，只选择 Theme 与业务高级组件范围；第二轮生成布局高级组件、局部
Template 和标准组件混合的 Hybrid Contract。旧 `UIBrief`、整卡评分和整卡参数映射代码保留但被主链路
旁路。Hybrid 原始输出由布局根编译器静态展开；可信端随后补齐 CardFrame，并复用 Terse Nested2 到标准
A2UI 的 Adapter。旧 `card@1` 编译入口保持不变，只服务兼容测试和代码级回滚。
高级组件展开后的动态字段在有效 TerseDSL 中使用完整 `${data.weather.temperature}` 占位值；占位值只能
来自本轮 TaskSpec `dataModelSchema` 的 `/data/...` 叶子，不能与静态文本拼接。确定性 Adapter 将其转换为
鸿蒙扩展 A2UI 的 `{{ ${/data/weather/temperature} }}` DataModel 绑定，初始 `updateDataModel` 仍按 TaskSpec
样例建立结构，端侧后续按 CardSpec 写入路径更新真实或 Mock 数据。
第四接口原路径每轮成功后将模型最终 Design Token 保存到 `designcompactdsl`；模板路径将展开后的标准
A2UI 确定性反向归档为 A2UI-Compact，并校验其再次转回的三段 A2UI 与 `genui` 逐对象完全一致后，保存到
同一 `designcompactdsl` 代码块。这样模板 create 产物也能直接作为后续第四接口 edit 的
`previousDesignToken`。第五接口新混合 create 路径
把 Template/布局已展开的有效 Terse 保存到 `designcompactdsl`，保证后续 edit 使用标准 Terse 协议；模型
原始 Hybrid 只进入受控评估证据和脱敏指标，不写生产 artifact。两者都将最终标准 A2UI 保存到 `genui`。
两个后端配置均可选择 `mep` 或 `openai`，调用方不能通过请求字段覆盖服务端
路由。`openai` 每个模型阶段都从配置的 master 开始；只有该阶段失败并耗尽 master 重试后才切换
fallback。模型成功返回后的 conversion/validation error 仍属于质量问题，不直接触发客户端切换。

DeepSeek Platform 的 AK、URL、模型名、业务 API Key、sender、receiver、messageName 和默认请求上下文
均来自服务配置。SK 只通过 STS 读取，默认 STS key 为
`genui.deepseek.platform.secret.key`，不得写入普通配置或日志。`sessionId`、`interactionId`、`deviceId`、
国家码、App 版本和 App 名称优先从当前 WebSocket 请求上下文获取，缺失时才使用配置或本次请求生成的
稳定标识；同一请求的首次生成、重试和 repair 复用同一上下文。

所有 `deepseek_platform` 和 `llmclient` 物理调用共享一个 SQLite 持久预算。每次发送真实请求前使用
`BEGIN IMMEDIATE` 原子预留，失败调用也计数；硬上限固定为 400，不能通过环境变量提高。默认数据库为
`workspace/runtime/deepseek_call_budget.sqlite3`，部署必须把它放在单实例可持久写目录。达到上限时立即
抛出 `DeepSeekCallBudgetExceeded`，禁止重试、fallback 或质量 repair 继续消耗。该预算当前保证同一数据库
上的线程/进程并发安全；多副本部署必须把各副本指向同一支持文件锁语义的持久卷，或在上线前迁移到
具有同等原子预留语义的共享计数服务。

输入内容包括：

- 用户原始 query
- 目标尺寸
- TaskSpec
- 协议 profile 摘要
- 美观规则
- 不可用能力的降级上下文

A2UI 模型输出只接受一个 `genui` 代码块，且恰好三行 JSONL：

```genui
{"version":"v0.9","createSurface":{}}
{"version":"v0.9","updateComponents":{}}
{"version":"v0.9","updateDataModel":{}}
```

模型生成的组件动态值、素材和点击行为必须分别遵循当前 profile 的表达式策略、素材策略和事件链策略；不得根据通用 A2UI 知识自行扩展当前 Form 子集。

端侧最少依赖：

- `genui`

## 校验与重试

校验对象是完整 artifact 文件，而不是只校验 DSL。

必查项：

```text
genui 恰好三行 JSONL
createSurface/updateComponents/updateDataModel 顺序正确
surfaceId 三行一致
catalogId 为规则配置允许的 `ohos.a2ui.extended.catalog`
createSurface 不声明 width/height；root 外围尺寸使用 `"matchParent"`
CardSpec suggestSize、必填静态字段和 dataBindings 结构合法
组件类型、组件顶层字段、事件和素材符合规则配置
children 引用可解析
完整表达式语法合法，长度和括号深度不超限，结构字段不使用表达式
PathBinding、FunctionCall 和表达式只出现在对应 schema 允许动态数据的位置
updateDataModel.value 不得在动态数据能力输出路径下新增未授权字段
DSL 绑定路径可从 updateDataModel.value、CardSpec outputSchema 或有效能力写入路径中推导
事件只使用 `onClick`，每个事件只有 1 个 handler，且不包含 `condition`、`as` 或 `$context`
事件 call/args 只能来自有效 eventCandidates，并符合对应参数 schema 和合法目标
图片只能来自有效 assetCandidates 或用户明确提供的本地资源；允许已声明的本地/资源路径 SVG，拒绝网络图、内联/base64 SVG data URI 和未声明路径
CardSpec 只包含有效 dataBindings
writeResultTo 不冲突
edit 模式的新 artifact URL 与来源 URL 不同
edit 模式已删除能力对应的绑定、事件和展示路径不再存在
```

DSL 转换、Artifact 校验和质量失败 repair 按以下规则控制：

- 小模型请求超时、连接失败、HTTP/流式事件异常、模型显式错误或没有生成非空 DSL，
  均属于模型生成失败，不属于 DSL 校验失败。
- 模型生成失败重试由独立开关控制，默认关闭。失败是否发生在真实模型调用边界是分类依据，不依赖
  MEP、DeepSeek Platform、llmclient 或上游网关是否返回规范错误码；模型调用抛出的异常、流式响应
  异常、显式错误和空输出
  均按同一策略处理。
- 关闭模型失败重试时，每次模型阶段只调用路由 master 一次，不重试且不切换 fallback。开启后，每次
  首次生成或 repair 都使用原提示词从 master 开始执行有限次数的指数退避重试。仅当
  `enable_openai_fallback=true` 时，master 耗尽后才切换 fallback，并按 fallback 独立次数配置重试。
  `model_failure_max_retry_attempts` 表示首次调用之外允许的最大重试次数，默认 `1`，合法范围 `1～10`；
  `fallback_model_failure_max_retry_attempts` 表示 fallback 首次调用之外允许的最大重试次数，默认 `1`，
  合法范围 `1～10`。两者在开关关闭时均不生效。
- 当 master、fallback 的额外重试次数分别为 `M/F`、质量 repair 上限为 `R` 时，重试开启后的单个模型
  阶段最多调用 `(1 + M) + (1 + F)` 次；整个请求最多调用
  `(1 + R) × [(1 + M) + (1 + F)]` 次。fallback 关闭时分别降为 `1 + M` 和
  `(1 + R) × (1 + M)` 次；重试关闭时每个模型阶段最多调用 master `1` 次。
- 退避名义时长从 `model_failure_retry_initial_delay_seconds` 开始，按
  `model_failure_retry_backoff_multiplier` 成倍增长，并受 `model_failure_retry_max_delay_seconds` 限制；每次
  等待叠加 `model_failure_retry_jitter_ratio` 配置的随机抖动，避免并发请求同步重试。等待使用异步 sleep，
  不占用线程和模型并发令牌，等待结束后重新参与共享模型并发排队，WebSocket 心跳继续发送。
- 模型失败重试与质量 repair 相互独立。conversion error 和 Validator error 不切换 fallback，而是由
  `enable_validation_failure_retry` 控制立即组装定向 repair；每轮 repair 重新从 master 开始，其中发生的
  模型调用异常仍使用上述主备和退避策略重试同一份 repair 提示词。
- 最终模型生成失败时不得调用后续校验器、不得保存 artifact。repair 最终失败时也不回退保存首次
  非法 DSL。
- 第四、第五接口的源 DSL 确定性转换始终执行，不受 Artifact Validator 开关影响；转换失败不得保存
  不可用 artifact。
- Artifact Validator 默认开启；关闭时只跳过 Validator，不跳过必要的源 DSL 转换。
- `enable_validation_failure_retry` 同时控制转换 error 和 Validator error 的定向 repair，默认关闭；
  warning 始终不触发 repair。
- 每轮修复请求的第二条 user 消息携带首次原始 user 内容、当前最新的完整源 DSL、源格式，以及结构化
  `qualityErrors`；每项 error 固定包含 `stage`、`code`、`message`。编辑模式的首次 user 内容已经包含来源
  artifact 的上一轮 `previousDesignToken`，但 repair 的直接修复对象始终是当前最新源 DSL。修复输出必须
  仍是当前接口的源 DSL 格式，再重新执行相同 Processor 和 Validator。
- 同一请求允许错误阶段在 repair 后发生变化，例如首次 `conversion` 失败、第一次 repair 转换成功但
  Validator 返回 `validation` error、第二次 repair 后全部通过；每次模型 repair 都消耗一次统一次数预算。
- `validation_failure_max_repair_attempts` 控制最多 repair 次数，默认 `1`，合法范围 `1～10`；全部
  error 消失时提前停止。每次 repair 内的真实模型异常仍独立受模型失败重试开关控制。
- 非法 DSL 和错误列表按不可信数据处理，不得覆盖原模式的协议、能力、素材、事件和输出格式约束。
- 修复日志只记录接口策略、失败阶段、错误数、当前/最大 repair 次数、提示词类型和模型后端，不记录
  修复请求载荷。
- 首次生成的提示词日志不得打印完整消息体；只记录消息数量、system prompt 总字符数，以及由
  `model_prompt_log_preview_chars` 控制的 system prompt 起始预览，默认最多 `30` 个字符。配置为 `0` 时
  不打印提示词正文，只保留长度和消息数量。
- repair 达到上限后仍无法转换时，第四、第五接口返回 `failed/VALIDATION_FAILED` 且不保存 artifact；
  已转换但仍有 Validator error 时，第三接口继续非阻断保存，第四、第五接口严格阻断。

标准 A2UI 校验逻辑内置于 `cloud/services/card_validation/`，由 `ArtifactValidator` 直接调用 Python API，不执行 `skills` 下的脚本，也不启动子进程。静态校验规则部署在 `cloud/data/validator_rules/`；动态数据、事件和素材白名单来自本次 artifact 的 `effectiveCapabilities`，能力详情从 artifact 记录的能力版本目录加载。第四、第五接口在源格式转换成功后校验标准 A2UI 结果；转换后的内容保存到 `genui`，模型最终原始 Design Token 保存到 `designcompactdsl`，只用于调试和下一轮编辑。

## 降级与拒答

主 Agent 看到的是候选能力，微服务才知道真实设备能力，所以主 Agent 不要提前说“可以生成天气日历卡”。推荐话术是：

```text
我先检查当前设备支持情况，然后为你生成可用的卡片。
```

处理规则：

```text
核心能力可用
 -> 正常生成

部分能力不可用
 -> 降级生成，说明少了什么

组件样式不支持
 -> 不拒答，改写为支持组件表达

数据能力不存在
 -> 不伪造动态 CardSpec，可做静态卡或入口卡

App 未安装
 -> 有入口或静态价值则降级，否则提示安装或启用

所有核心能力不可用且静态卡无价值
 -> 不调用 A2UI 模型，直接 unsupported
```

主 Agent 面向端侧的结果说明只保留以下三类异常或非完整满足话术；完整 `success` 仍使用正常成功说明：

```text
部分数据不支持：本次卡片生成暂无你提及的 XX 数据，将基于可获取数据为你生成卡片
整体不支持：抱歉，当前暂无法获取你提及的XX功能数据，你可以尝试生成首页精选的天气、日程、运动、设备电量等同类应用卡片
其它异常：卡片创建过程遇到问题了，请稍后再试
```

其中 `XX` 必须替换为用户能理解的数据或功能名称，模板中 `XX` 两侧的空格仅用于标示占位符，实际回复替换后不保留；例如输出“日程数据”，不要输出“日程 数据”。优先从用户原话、能力描述和微服务移除原因中提炼；多个名称用“、”连接，无法可靠提炼时替换为“相关”。不得使用能力 ID、provider、错误码或其它内部字段。部分数据不支持时继续基于可获取数据生成，并在取得有效 `artifactUrl` 后附带 `genWidgetResult`；不要再询问用户是否继续。整体不支持和其它异常不输出 `genWidgetResult`。除完整 `success` 外，主 Agent 不透传或润色微服务 `message`，编辑失败也不追加专属话术。

微服务内部状态需转为主 Agent 可感知的一系列描述：

```json
{
  "status": "degraded",
  "artifactUrl": "https://obs.xxx/widget/artifact_uuid.md",
  "message": "日历服务当前不可用，已先生成只包含天气的通勤卡片。",
  "removedCapabilities": [
    {
      "id": "GetCalendarEvents",
      "reason": "PACKAGE_NOT_INSTALLED",
      "userReadableReason": "日历服务当前不可用"
    }
  ]
}
```

示例 unsupported：

```text
抱歉，当前暂无法获取你提及的外卖配送功能数据，你可以尝试生成首页精选的天气、日程、运动、设备电量等同类应用卡片
```

示例 degraded：

```text
本次卡片生成暂无你提及的日程数据，将基于可获取数据为你生成卡片
```

### CLI Provider Bundle 与 CardTemplate PoC

为避免数据能力提供方同时维护不直观的 Python 展开代码，云侧支持由 CLI Provider 随能力交付
`card-provider-bundle/1`。一个 Bundle 以 `provider.json` 为唯一入口，并在同一目录内携带能力
对应的一个或多个 `.cardtpl`。正式能力注册表仍是 TaskSpec 字段及类型的只读权威来源，不要求其他团队为
Provider Template 增加字段或反向引用。Manifest 的单个能力关联只保留 `capabilityId`、`dataSchema` 和
`templates`；其中 `dataSchema` 只包含 `path` 与 `version`。

Bundle Loader 先在云侧 `data` 根目录下解析 `dataSchema.path`，用于引用已有上游 Schema；文件不存在时
再按 Bundle 内相对路径解析，由 Provider 自带本地 Schema。引用上游文件时，路径必须包含声明的
`dataSchema.version`。上游文件若为正式能力列表，Loader 按 `capabilityId` 选出唯一能力的
`outputSchema`；本地文件也可直接是 JSON Schema。解析出的 Schema 直接用于检查 `.cardtpl` bindings 的
相对 JSON Pointer 与类型，不再维护额外的字段投影锁、Schema 摘要或职责标识字段。Manifest 仍声明
Provider ID/版本、模板文件 SHA-256，以及 `cardtpl/1`、`ohos.a2ui.extended.catalog`、A2UI `v0.9`
兼容信息；加载失败时关闭整个 Bundle。

请求阶段不重新解释或改写正式能力注册表。服务端根据本轮 CardSpec 中同 `capabilityId` 的唯一
`writeResultTo`，检查 TaskSpec 是否包含该 Provider Template 的全部绑定路径且类型兼容；不满足时在模型
Prompt 构造前只移除该 Template，并记录 `provider_template_disabled`，正式数据能力和通用生成链路继续
可用。Compiler 保留相同检查作为最终门禁。该运行时失配不能关闭正式能力，也不能导致服务启动失败；
构建/CI 的 Schema、binding 或模板摘要失配仍按 Bundle 错误严格失败。

`.cardtpl` 只是一种声明式 Template 源码，不是 Python、ArkTS 或通用脚本。当前 PoC 的闭合语法如下：

```text
#Template("WeatherOverview@1", {
  capability: "ViewWeather",
  bindings: {
    city: { path: "/location/districtName", type: "string" }
  },
  ...
})
#Variant("hero", {
  sizes: ["2x2", "2x4"],
  roles: ["hero"],
  requires: ["city"]
})
Column("compact",
  Text(Bind("city"), "compact-title"),
  Text(`${condition}｜${airQuality}`, "body")
)
#EndVariant
#EndTemplate
```

指令参数只接受 JSON 字面量；模板体只接受白名单标准组件、容器、`Bind/Param/Asset` 引用、受限反引号
字符串、`Expr`，以及 `IfParam/IfMissingParam/IfBind/IfMissingBind` 声明式结构守卫，不接受属性
访问、变量、函数定义、导入、循环、条件、解包、关键字参数或任意函数调用。Parser 将源码编译为现有
`TemplateDefinition/TemplateNode/TemplateValue` UI IR，逐个 Variant 校验尺寸、角色、必需绑定、参数
Schema、节点数和深度预算；运行时仍由现有可信 Template Compiler 展开并经 Terse UI IR → A2UI Adapter
输出。最终 `genui` 只能包含标准 A2UI 组件，不能包含 `Template`、`Bind` 或 Provider 私有组件。

`Bind("city")` 表示相对能力输出 Schema 的稳定字段，不写死业务请求的运行时根路径。展开时服务端用
Template 的 `capability` 找到本轮 CardSpec 中同能力唯一的 `writeResultTo`，将二者拼成完整 JSON
Pointer，并再次检查该叶子存在于 TaskSpec 且类型一致。例如 `/location/districtName` 在本轮绑定根
`/data/weatherPoc` 下解析为 `/data/weatherPoc/location/districtName`，随后确定性输出 A2UI path
binding。根路径缺失/歧义、字段越界、数组路径错误、类型不符或路径无法编码时均拒绝展开，不允许用
样例值相等、字段名猜测或静态默认根路径兜底。

反引号字符串使用 TypeScript 风格的 `${bindingName}`，例如
`` `${condition}｜${airQuality}` ``。普通插值占位符只允许引用当前 `bindings` 中声明的 string 标识符，
不允许 `${condition.value}`、函数调用、嵌套插值或类型转换。需要数值运算、比较或三元选择时必须显式使用
`Expr(\`...\`)`，并通过独立表达式语法白名单。Compiler 将已闭合校验的 binding 和
静态字面量确定性编译成单个 `Text.content` 完整 A2UI 表达式：
`{{ ${/data/.../condition} + '｜' + ${/data/.../airQuality} }}`。Compact 转换器只放行占满整个字符串的
JSON Pointer、单引号字符串和 `+` 拼接，并把所有引用继续纳入 DataModel、TaskSpec Schema 和 CardSpec
数据根校验；生成期不读取 `sampleValue` 计算具体字符串。温度去单位等非拼接转换应由数据能力提供展示
就绪字段，或后续单独注册有类型约束的安全转换，不能先在 Python 中改写样例字符串再依赖值相等反推绑定。

当前天气 PoC 注册 `com.huawei.weather.cli` 的 `ViewWeather`，提供 `compact/compactIcon/hero/heroIcon`
四个 Variant，覆盖
地点、温度、天气现象、空气质量和当日高低温五个动态绑定。验证范围包括 Bundle 正常加载、上游 Schema
解析、Bundle 本地 Schema 兜底、上游版本路径失配拒绝、未声明 Bind 拒绝、请求缺少能力根或字段时关闭
候选、错误 CardSpec 根路径拒绝，以及
`Template → UI IR → 标准 A2UI` 端到端展开。天气已完成第一轮 Python 影子对比门禁：四个 Variant
保留五个独立动态路径，图标 Variant 使用 20vp 天气图标，Hero 温度保持 38fp，并由编译期
`_advancedComponent` 元数据复用天气专用布局归一化；该元数据在最终 A2UI 输出前剥离。
`WeatherOverview` 已把 UX Registry 默认实现切换为 `WeatherOverview@1`，可信 Python 展开只保留为
测试 Shadow Oracle，不参与生产失败回退。Provider Template 与业务高级组件的正式关联只记录在本仓 UX Registry 的
`localTemplateIds`；Compiler 仅对本轮 `requiredLocalTemplateGroups` 中的 Template 解析该映射，复用
天气、电量等跨业务布局约束。独立模板验证不会被误判为生产业务组合，正式能力注册表也不需要反向引用
模板或业务组件。
本轮同步验证还发现，Python 路径先把天气现象和空气质量拼成新字符串后，现有按样例值相等绑定的逻辑
无法恢复这两个独立动态路径。Provider 反引号插值改为单 `Text` 完整 A2UI 表达式后，两个 JSON Pointer
既能独立校验和更新，也保持原单文本布局语义；该表达式结构和最终引用路径作为后续默认路由切换的功能
门禁，不能用纯视觉断言替代。

批量整改覆盖 UX Registry 原先使用 `terse-dsl` 直接展开的 11 个业务组件：天气、日期、日程、电量、
系统内存、应用使用时长、活动、运动、心率、睡眠和蓝牙耳机。数据提供方按能力组织 Provider Bundle；
同一能力可交付多个垂域 Template，同一业务组件由不同能力提供数据时可注册多个候选 Template。正式
能力注册表存在对应 Schema 时优先引用其只读路径；`GetSystemMemInfo` 等尚无上游路径的能力由 Provider
携带本地 Schema。模板只能绑定上游实际存在的字段，星期、状态判断、时长拆分等派生事实不得通过静态
样例或字段名猜测补造。

两阶段迁移已经闭合：全部 11 个原直接展开组件均已交付声明式 CardTemplate，并完成逐组件结构、关键样式、
Action、动态绑定、业务分支和组合约束的 Python-vs-Template 等价回归；生产默认路由统一为 `template`。
请求投影只从 CardSpec 的唯一 `writeResultTo` 根复制模板声明的绑定叶子，不复制整个能力输出，避免
Provider Template 准入与模型 Prompt 使用不同数据视图。缺少必需字段时关闭对应 Template/Variant，不能以
模板静态文案代替真实数据。

#### 第四接口的模板优先路由与双协议归档

`generateWidgetCardCompactDsl` 只在 create 模式尝试模板优先路由，顺序固定如下：

1. 沿用原 dev 主流程完成能力裁决、CardSpec 和 TaskSpec 构造，不修改正式能力注册表。
2. 首层 LLM 输出严格的 `template-route-decision/1`，只包含 `templateUsable`、`themeId` 和
   `advancedComponentIds`。Prompt 同时下发用户 Query、每个能力的 `candidateOutputFields`，以及候选业务
   组件各 Provider Template Variant 的字段覆盖集合。
3. `templateUsable=true` 不是最终授权。服务端再次验证组件准入、尺寸、主题、组合布局和数据完整覆盖；对
   每个候选能力都要求存在非空 `candidateOutputFields`，并证明所选一个或多个业务组件存在一组实际
   Template Variant，其 binding 并集覆盖全部 Query 筛选字段。任何一个字段未覆盖、能力根重复、字段证据
   缺失、模板缺失或首层结果不合法，均视为模板判断失败。
4. 模板判断失败时，原请求、TaskSpec 和能力裁决结果不变，继续执行 dev 分支原 Design Compact Prompt、
   Processor、Validator、repair 和 artifact 保存流程。只有首层判断阶段允许该回退；模板已经选定后，
   第二层生成、受限展开或契约校验失败按模板生成失败返回，不能静默改走另一套视觉逻辑。
5. 模板判断成功后，第二层只选择批准的布局、Provider Template Variant 和可信素材/动作，服务端静态展开
   为标准三段 A2UI。最终 `genui` 保存标准 A2UI；服务端再执行确定性的 `A2UI → A2UI-Compact` 归档，将
   组件语义属性与 `styles` 合并回 Compact 行、恢复尺寸对应的 root 设计尺寸并保留 DataModel 行。
6. 归档结果必须通过现有 Design Compact Processor，并再次转换为标准 A2UI；三段消息逐对象与模板产出的
   `genui` 完全一致才允许上传 artifact。任何不支持属性、树结构、数据路径或往返差异都阻断保存。

edit 模式以非空 `sourceArtifactUrl` 为判据，始终跳过首层模板判断和第二层模板生成，直接读取来源 artifact
中的 `designcompactdsl` 作为 `previousDesignToken` 进入原 dev 编辑流程。因此模板 create 成功时同时归档
标准 A2UI 与可编辑 A2UI-Compact，是后续二次更新可用性的强制条件，而不是可选诊断信息。

日期/日程、电量/耳机、内存/电量、活动/睡眠、活动/心率和运动/活动组合继续由 Compiler 按原业务组件关系
执行固定顺序、角色和 Action 归属校验，Provider Template 不能通过改名或嵌套绕开布局约束。日期格式、
日程 `timeText` 和时长拆分等上游未提供的展示分段由受类型约束的确定性投影产生；`${...}` 动态字符串和
`Expr` 运算始终保留为端侧 A2UI 表达式，不在生成期投影样例值。

可选素材使用 `IfParam/IfMissingParam`，可选 Provider 字段使用 `IfBind/IfMissingBind`。编译器要求所有可选
引用处于对应守卫内，并在 TaskSpec schema 中决定分支；守卫在最终 A2UI 前消除。Battery Variant 还必须与
可信 normal/charging/low 状态一致，Bluetooth Variant 必须与连接态、字段形态、尺寸及手机组合关系一致。

最近运动与运动倒计时仍属于同一个 `WorkoutOverview` 业务能力，根据 CardSpec 实际绑定能力分别选择
`WorkoutOverview@1` 或 `WorkoutCountdown@1`。Provider Template 根节点携带服务端内部
`_advancedComponent` 标记，使布局、Action 归属、组合顺序、主题前景处理和 CardSpec 标题策略继续按原
业务组件执行；该标记与全部结构守卫均在最终 A2UI 前移除。保留的 Python 构造只参与 Shadow Golden，
不存在模板失败后的生产 Python 回退。

主题颜色以 `UX设计/卡片颜色风格.md` 为唯一视觉基线，并在云侧 Theme Registry 与可信 Compiler 中
确定性落地，第二层模型不能输出任意颜色。标准浅色卡片使用白色基底与场景色 10% 到透明白的渐变：
通用功能/内存使用 `#0A59F7`，耳机使用 `#64BB5C`，低电使用 `#F9A01E`，日程使用
`#E84026`。强视觉卡片使用实色渐变：晴天 `#317AF7` 到 `#46B1E3`，雨天 `#46484D`
到 `#467794`，睡眠 `#AC49F5` 到 `#C386F0`，运动/赛事 `#ED6F21` 到
`#F9A01E`。浅色卡正文使用黑色 90%/60%/40% 层级；强视觉卡普通文字和单色标题图标使用白色，
天气多彩图标保留原色，晴天 sun 语义图标使用黄色，雨滴/云/风暴/雪等明确单色天气图标使用白色。
正常数据可视化使用 `#64BB5C`，预警/低电使用
`#F9A01E`，轨道使用 10% 黑。功能按钮按规范使用场景色 10% 背板与同色文字；强视觉卡使用白色
背板与场景色文字。颜色在 A2UI 中统一写为 ARGB 八位值。

多业务跨领域 Scope 不再强制降级为通用白色主题。服务端先验证模型 Theme 是否属于所有选中业务组件
声明场景的并集；模型选中不兼容 Theme 时，按业务组件顺序选择第一个非 generic 场景 Theme，只有没有
非 generic 场景时才使用通用 Theme。这样天气+电量保留天气主视觉，内存+电量保留内存浅蓝主视觉，
同时所有辅助业务文字和单色图标由最终 Theme 的前景角色统一校正。

第一层 Scope Prompt 只下发最多 8 个基于 Query 与 Schema 语义排序的业务组件候选、兼容组合和 Theme，
输出字段固定为 `scopeVersion/themeId/advancedComponentIds`。服务端校验组件是否来自本次候选、尺寸预算、
Palette Scene 和是否至少存在一个共同布局。`WeatherOverview` 只有在 `ViewWeather` 数据中能确定性取得
`city/temperature/condition/airQuality/temperatureRange` 五个类型正确且非空的事实，并且用户未请求
小时预报、日出日落、气压、能见度、AQI 数值、体感、湿度、风、紫外线、预警、降雨概率或未来预报等
未支持数据时，才进入候选；模型返回后服务端
再次执行相同复核。第二层只看到允许布局、对应局部 Template 的 variant/参数 Schema、业务事实
和标准组件能力。布局配置默认省略；需要覆盖默认重排时，只允许一个位于业务 child 前、
由 Registry 闭合 Schema 校验的对象，不能写任意坐标、尺寸或样式。业务组件由局部 Template 与标准组件
实现，不形成端侧私有节点。`WeatherOverview` 由受限
`Template("WeatherOverview@1", "heroIcon|compactIcon", { conditionIcon })` 调用展开为标准 Terse 节点；
地点、温度、天气、空气质量和温度范围由服务端绑定为 `${data...}`，模型只选择闭合 Variant 和可信天气图标。
地点固定在标题 Row 的 leading、天气图标固定在同一 Row 的 trailing，2x2 温度使用 38fp，并按 2x2/2x4 与
hero/support/peer 角色确定性重排。Weather 的标题、内容和布局承载区使用 `matchParent` 填充父区域，禁止
用渲染器会按 100vp 处理的 `"100%"` 充当百分比；2x2 单业务按标题 Row、38fp 温度、底部天气/空气质量/高低温的顺序结构排列，不再用上下 Overlay 相互叠放。天气图标统一为 20vp；第二步选择的素材具有 `sun/sunny` 语义时直接注入黄色 `fillColor`，不再依赖天气文字重复判断；雨滴/云/风暴/雪等单色素材在强背景上注入白色，内置 `icon_weather*`/`weather_icon*` 彩色渐变素材和其它多彩图标保留原色，避免端侧被单色 tint 渲染成实心方块。`event.open.weather` 天气详情 Action 降级为 CardFrame 整卡 `onClick`，不生成 PillAction/IconAction 可见按钮；整卡点击不得被视为 Action 按钮而跳过正文白色前景规则。拨号、导航等其它动作仍使用布局 Action 区。多业务不生成未来预报列表；没有独立 forecast 业务
组件时不允许 `WeatherNowForecastLayout`。
TaskSpecBuilder 对 `ViewWeather.location.districtName` 使用本轮绑定参数中的非空 `districtName` 覆盖注册表
展示样例，避免请求“上海”却按静态样例显示“青浦区”；没有可信请求参数时才保留 schema 样例。

`DateOverview@1` 和 `ScheduleOverview@1` 均由 `com.huawei.calendar.cli` 交付并绑定
`GetCalendarEvents.events[0]`。日期模板开放 `compactDate/dateHero`，分别绑定 `startDate` 以及可选的
首项标题；日程模板开放 `nextEvent/meetingCompact/meetingExpanded`，绑定 `title/dtStart/dtEnd`，其中
`meetingExpanded` 额外要求 `eventLocation`。2x2 日期+日程固定使用 `compactDate + meetingCompact`，
2x4 使用 `dateHero + meetingExpanded`，缺地点时降级为 `meetingCompact`。模型只输出相应
`Template("...@1", "<variant>", {})`；日程 Action 仍只能位于布局末尾，由批准的 `eventCandidates`
注入，模板不得读取业务数据中的链接字段自造事件。

`AppUsageOverview@1` 由 `GetAppUsageDuration` 提供，只开放 `singleApp`，并直接绑定
`appUsage.appName/appUsage.durationText/updatedAt`。`BatteryOverview@1` 由 `GetPhoneBatteryInfo` 提供
`normal/charging/low`，根据 Variant 精确要求 `batterySOC/batterySOCText/chargingStatusDesc/
batteryCapacityLevelDesc`。`ResourceUsageOverview@1` 使用 Provider 本地 `GetSystemMemInfo` Schema，只开放
`memory` 并绑定 `usagePercent/availableMemText/totalMemText`。缺字段、类型错误或越界时关闭对应
Template/Variant；时长、百分比、状态文案均使用上游展示就绪字段，不在 CardTemplate 内转换或推断。

运动健康 Provider 同时交付 `ActivityOverview@1`、`WorkoutOverview@1`、`HeartRateOverview@1` 和
`SleepOverview@1`。Activity 的 `steps` 只要求 `dailySteps`，`dailySummary` 还要求热量与距离；Workout
的 `latest` 绑定运动类型、时长和热量，倒计时则按 CardSpec 的 `GetCountdownDays` 绑定改用独立
`WorkoutCountdown@1/countdown`。Sleep 的 `duration` 只要求总时长，`insufficient` 额外要求可信状态，
`schedule` 仅用于 2x4 且同时具备入睡和醒来时间。所有拼接文本统一使用受限反引号 `${...}` 语法，最终
仍保留为独立动态绑定，不允许表达式、转换或跨记录拼接。

`BluetoothDeviceOverview@1` 绑定 `GetEarphoneInfo`，按实际存在的字段开放 `earbuds/leftEarbud/
rightEarbud/earbudPair/earbudsFull`；服务端优先下发信息最完整且全部 required bindings 可满足的 Variant。
手机电量+耳机、内存+电量等组合继续使用原固定布局、主辅顺序和 Action 归属约束。Compiler 根据模板根的
内部 `_advancedComponent` 标记把 Provider Template 映射回业务组件执行校验，并在生成标准 A2UI 前移除
该标记。

第二层输出多个顶层 sibling call 时，仅当顶层恰好包含一个本轮批准的 Layout call，Framer 才尝试修复。
若 Layout 内没有业务模板且外部恰好有一个 `Template(...)`，Framer 将该模板放回业务槽位并保留末尾
Action；存在零个或多个合法 Layout、多个外部 Template 或旧直接业务 wrapper 时硬失败。Framer 只修复
结构，不绕过 Template、binding、业务组合或 Action 契约。

应用管控、省电、内存清理、运动健康、睡眠提醒等动作仍必须同时满足用户意图和已批准事件候选；Action
只能作为布局连续末尾 children，素材只能逐字引用本轮白名单。没有批准动作时使用无动作布局，不在模板内
生成按钮、默认事件或占位图标。

Selector 与领域规则只使用用户 Query、TaskSpec Schema 和版本化注册表，不读取 Fixture ID、Golden 场景
名或业务专用布局源码。日程时间、待办完成率与逾期、通话摘要、电量状态、App 使用比例、运动与睡眠时长、
位置新鲜度、系统模式互斥和蓝牙分部件状态仍由可信 Python 规则计算，LLM 不能覆盖这些计算。

模型输出后的 Validator 检查目标尺寸、布局根、布局子项数量、布局 Action 条件、业务组件/列表/Action/
Chart/层级预算、`0/null`、可用性、隐私和可信 Template 映射，再执行 Hybrid Parser、Template 参数
Schema、Action/素材/字面量、节点/深度/空间及标准 A2UI 校验。2x2 通常使用 1 至 2 个业务组件、最多
3 个；2x4 通常使用 2 至 3 个、最多 4 个；两者最多 1 个主 Action 和 1 个主 Chart，列表项分别最多
2 和 3。`ActionMatrixLayout` 是唯一例外：保持一个主动作语义，但可按 2x2/2x4 契约使用 2 个或
2 至 4 个不重复 `ActionTile` 控制命中区。模型失败不能使用旧整卡入口、高级计划或 Golden 生成替代
artifact。

模型直接输出布局高级组件根；可信端按 10 种布局各自的确定性算法降级，不能把不同布局统一降为相同的
Stack/Column。布局配置必须位于业务 child 之前，Action 必须连续位于末尾，并按尺寸契约检查业务/Action
数量。固定高度或宽度区域显式设置零最小约束，避免文本默认最小尺寸挤压主内容。服务端把候选事件和标签
绑定到 `PillAction`、`IconAction` 或 `ActionTile`，并强制执行对应的高度、图标、圆角和字体 Token。
独立 Header 默认省略，业务标题由业务 Template 或标准 Text 呈现，不再从 Query 截取卡片标题。可信端只
在布局降级后补齐 `radius=20/safeInset=12` 的 CardFrame。2 至 4 个较短的缺失必需事实会合并为一行补齐，
避免逐项纵向堆叠挤压主内容。2x2 `HeroSupportActionLayout` 的 Support 最多两行；空间不足时删除非必需
Support，若其中包含必需事实则拒绝该输出并由第二层修复，不能裁切 Support 或压缩 Hero/Action。

旧 `advanced-component-registry/1` 的 15 个组件族、8 个自适应模板、`hero/support/micro` 角色和整卡插件
选择代码保持原样，继续由旧 `AdvancedComponentPipeline.generate()` 的兼容测试覆盖。它们不参与第五接口
create 主链路，除非后续通过显式代码回滚重新接线；不得通过普通请求参数切回旧路径。

不要靠主 Agent 保证视觉质量。微服务通过 prompt、候选素材和校验器保证。

硬规则：

- 单一主焦点。
- `2x2` 最多 3 个主区域。
- `2x4` 最多 4 个主区域。
- 受保护文本不截断。
- 字号只使用批准阶梯：`10/12/14/16/18/20/30/32/38/40`。
- 间距只使用批准阶梯：`2/4/6/8/10/12/14/16`。
- root shell 必须完整：`width/height/padding/borderRadius/clip/background`；其中 root `width/height` 必须写
  `"matchParent"` 且 `clip` 固定为 `true`。第五接口新 UX 混合 create 路径统一使用 `borderRadius=20`、
  `padding=12`；其它既有路径继续按 `2x2=18`、`2x4=22`，内部布局仍按 profile 目标尺寸预算。
- Row/Column 宽高预算必须成立。
- 图片必须来自素材白名单，且设置明确 `width/height/objectFit`。
- 允许素材白名单中的本地/资源路径 SVG；禁止网络图、内联/base64 SVG data URI、未声明资源路径、emoji 和纯装饰堆叠。

生成失败或视觉风险高时，强制降级为：

```text
标题 + 主状态 + 1 条支撑信息 + 1 个入口
```

## OBS 与端侧标记

微服务上传完整 artifact，不只上传 DSL。

多轮编辑读取来源 artifact 时复用 `utils/download_file_from_url.py` 的公共 `download_file` 方法。下载模式由 `enable_artifact_download_mock` 控制，默认开启：开启时从 URL path 提取文件名，只读取服务 `workspace/mock_obs`，文件缺失不访问网络；关闭时将原始 URL 交给公共下载方法，不跟随重定向，并传入来源 artifact 的超时和最大文件大小限制。repository 不再校验 URL 的来源范围。

返回：

```json
{
  "status": "success",
  "artifactUrl": "https://obs.xxx/widget/artifact_uuid.md",
  "artifactDigest": "sha256:xxx",
  "suggestSize": "2x4",
  "message": "已为你生成通勤卡片。"
}
```

Skill 输出流式标记：

````text
```genWidgetResult:"https://obs.xxx/widget/artifact_uuid.md"```
````

端侧识别该标记后下载 artifact。不要在普通自然语言中伪造该标记。

端侧下载后拿到 `genui + cardSpec`，用于预览、确认添加和后续刷新。

当 `generateWidgetCard` 工具不可用、调用失败或返回产物不符合预期时，主 Agent 按 `failed` 回复并终止本轮，不输出 `genWidgetResult` 标记，也不自行生成或上传替代 artifact。

## 开发约束

开发代码时遵守：

- 不把最终 CardSpec、DSL 或 artifact 生成逻辑放到主 Agent；该约束没有工具异常例外。
- `generateWidgetCard` 工具不可用、调用失败或返回产物不符合预期时，主 Agent 必须终止本轮生成，不得生成替代产物或伪造动态能力、`artifactUrl`、`genWidgetResult`。
- 不把 A2UI 协议白名单散落在多个模块中；统一由 `A2UIProtocolRegistry` 提供。
- 不让 A2UI 模型自行选择未过滤能力。
- 不让 A2UI 模型生成或修改 CardSpec。
- 不把点击事件写入 CardSpec。
- 不让 A2UI 模型生成 `onClick` 以外的 Form 事件、多个 handler、`condition`、`as` 或 `$context` 事件上下文。
- 不把结构 JSON Pointer 改写为表达式，不在不支持动态数据的位置使用表达式、PathBinding 或 FunctionCall。
- 不使用网络图片、内联/base64 SVG data URI 或未声明资源路径；本地/资源路径 SVG 必须来自有效素材候选或用户明确输入。
- 不在 TaskSpec 顶层扩展非协议字段。
- 不在校验失败后无限重试。
- 不在能力不可用时伪造动态 dataBinding。
- 不上传半成品 artifact。
- 不只返回 OBS URL 而丢失结构化状态。
- 不让主 Agent 下载来源 artifact 或直接编辑 DSL。
- 不把 `sourceArtifactUrl` 直接放入 A2UI 模型 prompt。
- 不在 edit 模式来源加载失败时静默执行首次生成。
- 不覆盖任何来源 artifact；每轮编辑都上传新对象。

## Nested-2 批量用例评测持久化

`generateWidgetCardTerseDslNested2` 支持仅面向受控评测环境的批次记录。端侧在 WebSocket URL 查询参数中
同时传入 `batchId`、`caseId` 和 `size` 后，微服务把本次调用关联到一个批次；缺少全部参数时保持正式工具
调用行为不变，部分缺失或值非法时拒绝该评测连接。批测记录由
`WIDGET_SERVICE_ENABLE_WIDGET_BATCH_RECORDING` 独立开关控制，默认关闭，生产环境不得仅为了普通生成打开。

批量视觉评测可临时同时开启
`WIDGET_SERVICE_ENABLE_ADVANCED_COMPONENT_DATA_ADMISSION_BYPASS_FOR_BATCH=true`。该开关只在批次记录开启时
且 WebSocket 同时携带合法 `batchId`、`caseId`、`size` 时生效，不能全局放宽普通生成请求。第一层候选暴露
和 LLM Scope 输出复核暂不执行各业务组件的字段完整性、查询细分及动作闭环适配判断，第二层 Template 候选也不再因
参数数据匹配不完整而提前剔除；批测 TaskSpec 从已
裁决能力的完整 `outputSchema` 恢复受控 `sampleValue`，避免候选已经开放但 `candidateOutputFields` 恰好缺少
高级组件必需展示字段。CardSpec 仍保持原始动态绑定与字段投影，不因批测扩充运行时数据契约。capability/
provider、目标尺寸、Registry 组合、二层可信事实投影、素材/Action 白名单、受限 Parser/Compiler 和最终
A2UI 校验仍保持。批测结果的 invocation 记录 `temporaryDataAdmissionBypass=true`；完成批测后关闭该开关即
恢复严格准入。

批次 ID 和用例 ID 只能使用字母、数字、点、下划线和连字符，长度不超过 64；`size` 只接受 `2x2` 或
`2x4`。批次第一次出现时自动创建，不新增一次模型调用，也不修改正式生成请求 schema、CardSpec、artifact
或工具业务响应；只有同时开启上述临时准入开关时，批测 TaskSpec 与模型 Prompt 才按上一段扩充可信样例字段。

每条用例在服务器持久卷中原子保存：

- 原始 WebSocket JSON 输入；
- 两步模型各自的完整输入 JSONL、原始输出和耗时元数据；这些文件只在批测开关开启时进入忽略目录，不进入
  工具响应或生产日志；
- 投影后的 TaskSpec、编译前已 framing DSL，以及 Weather 的 requested/renderable/visible 字段名和数量；
- 结构化业务响应和实际发送的 final 插件帧；
- 从同进程 `GenerateWidgetCardResponse.renderMessages` 还原的标准 A2UI JSONL；
- 服务端总耗时、开始/完成时间、requestId、状态、错误码、artifact URL 和摘要。

即使 final 响应通道断开，只要生成处理已经结束，也必须先落批测记录再尝试发送指令或 final 帧。请求校验
失败和未捕获服务异常同样记录失败结果；批测记录失败只能写错误日志，不能改变正式生成结果。记录目录使用
`WIDGET_SERVICE_WIDGET_BATCH_RESULTS_PATH`，必须位于服务持久卷中并保持在版本控制忽略范围内。

查询和下载接口：

```text
GET /api/v1/widget-batches
GET /api/v1/widget-batches/{batchId}
GET /api/v1/widget-batches/{batchId}/download
```

下载接口返回 ZIP，包含批次 `manifest.json` 以及每条用例的 `input.json`、`response.json`、两步模型
`*-input.jsonl`/输出文件、`diagnostics.json`、`output.a2ui.jsonl` 和 `metrics.json`。当配置了
`WIDGET_SERVICE_WEBSOCKET_BEARER_TOKEN` 时，这三个 HTTP
接口与工具 WebSocket 使用同一个 Bearer Token；开关关闭时返回 404，不暴露服务器目录。端侧测得的耗时
只用于现场观察，报告以服务器 `durationMs` 为准。

## 日志与监控

WebSocket 路由收到请求后，先从原始 `session` 中提取 `sessionId` 和轮次 `interactionId`，按现有规则组合为
requestId 并写入日志上下文，再输出紧凑的结构化摘要。凭据、API key、token 和测试授权在所有环境都递归
移除。`enable_sensitive_log_fields=false` 时继续移除用户/设备标识；只要 `WIDGET_SERVICE_ENV` 不是
`local` 或 `test`，还会强制移除 query、Prompt、原始/有效模型输出、A2UI、数据样本和请求响应正文，配置
不能关闭这条生产保护。完整 Prompt、原始输出、usage 和 finish reason 只允许由显式 Golden 评估命令写入
权限为 `0600` 的忽略目录，不进入生产日志、artifact 或版本库。

每次生成必须记录：

```text
requestId
deviceId 脱敏标识（不记录 uid）
queryHash
skillVersion
protocolProfileId
capabilityRegistryVersion
candidateCapabilities
effectiveCapabilities
removedCapabilities + reason
status
errorCode
latencyByStage
retryCount
artifactDigest
generationMode
sourceArtifactUrlHash
sourceArtifactDigest
```

关键指标：

- 生成成功率
- 降级率
- unsupported 率
- failed 率
- 校验失败率
- 重试成功率
- 平均耗时 / P95 耗时
- 各能力不可用原因分布
- 首次生成与编辑请求分组成功率、降级率、校验失败率和 P95 时延
- 来源 artifact 加载失败率
- 连续编辑轮数分布
- WebSocket 进程级运行统计：当前活跃连接数、进程启动后的累计连接数、当前正在处理的任务数；服务每 10 秒打印一次。
- 第一、第二接口的同步查询通过 AnyIO 工作线程执行，默认并发令牌数为 80；第三至第五接口直接
  `await` 异步生成 Service，不再让长耗时模型请求占用 AnyIO 默认工作线程。
- 应用生命周期持有唯一模型 Runtime。MEP 使用共享 `httpx.AsyncClient` 异步连接池；DeepSeek Platform
  使用异步 WebSocket；同步 llmclient 保持原实现并由专用线程池适配。三种物理客户端、三个生成接口、
  create/edit、首次生成、模型失败重试、fallback 和 repair 共用同一个进程级 Semaphore，默认真实模型
  并发上限为 20。
- 模型排队超时和实际执行超时分开配置，默认均为 120 秒。排队发生在协程中，不占线程；等待期间
  WebSocket 心跳、`/health`、能力概述和 Schema 仍可响应。每一次真实模型调用单独重新获取令牌。
- llmclient 执行超时后继续持有令牌，直到后台物理调用真正结束，再按超时返回，避免提前释放导致
  实际模型并发突破上限。心跳发送确认响应通道断开时，只停止心跳发送，不取消内部生成、repair 或
  artifact 保存。
